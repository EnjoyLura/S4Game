# 后续美术资源体积策略

本轮保持原画和完整动画；已使用无损WebP，完整包约351.47MB。要继续明显降低下载量，需要同时处理素材尺寸、内容组织和编码。预加载负责等待体验，分包负责按需访问；两者都不会自动减少完整资源的字节总量。

## 1. 运行资源与母版分开

本地保存原始生成图、视频、分层文件与中间帧。发布只带当前运行时依赖，继续使用现有未用资源归档、独立发布仓库、内容哈希和导出预算。制作母版的分辨率可以足够大，交付给游戏的纹理尺寸依据实际显示需求决定。

新增素材应标注：出现页面、首次出现时机、最大显示物理像素、是否透明、是否九宫格、是否被详情放大、所属英雄／章节。新增页面在 `LobbyArtWarmup.ts` 补齐小范围预测依赖，避免恢复全量 `resources.loadDir`。

## 2. 优先审查大图标的运行尺寸

当前有76张边长至少1024的方形PNG审查候选。三选一卡图是124设计单位，但还需要检查本局强化、详情和其他复用位置。按每张图的最大实际物理像素制定512／768／1024运行档，保留完整母版。

边长减半，基础RGBA纹理像素数变成四分之一；文件大小的减少需要实测编码。不要把DPR直接当成设计尺寸倍率，也不要统一缩小所有图片。采样与锐度仍需手机静态对照后采用，当前没有自动替换正式素材。

## 3. 动画裁透明边并紧密排布

当前八张4096×3584英雄图集各有56MiB基础RGBA8纹理。逐帧保留四像素余量后的有效矩形面积，前轮审计发现约35%～51%的留白优化空间；实际图集需要计入排布损耗，不能直接按此比例宣称内存下降。

播放器需要支持原画布、裁剪偏移、固定脚底和边缘过滤余量，再重新排布图集。每张裁剪帧还原到原画布后应逐RGBA比较一致，保留全部帧、原始顺序、帧时长、释放时机与镜像。透明区已经容易被WebP压缩，这一步的主要收益通常在纹理面积和内存，下载量要另测。[Cocos图集说明](https://docs.cocos.com/creator/3.8/manual/en/asset/atlas.html)

## 4. 大背景和插画做高品质WebP对照

前轮四个Q90本地样本，相对原PNG节省约81%～95%；正式仍采用无损编码，这些比例不能再叠加到当前351MB包。背景、卡面纸纹、装备插画可以逐类做原图／候选对照；文字、细线、透明边缘要单独检查。

有损编码会改变RGB。可先取Q95等保守档，依据手机实际大小和100%像素对照决定，不能承诺所有图片都像素相同同时再压缩80%。候选仍保存在本地 `D:/AI/S4Game/.local-art-archive/art-resource-v82-comparisons/index.html`。

## 5. GPU格式与资源生命周期

WebP降低下载字节，加载后仍要解码。ASTC／ETC2等GPU压缩针对纹理内存，需按设备支持、透明度与回退体积评估；同一台设备只取选定版本。[Cocos纹理压缩说明](https://docs.cocos.com/creator/3.8/manual/en/asset/compress-texture.html)

章节地图、英雄动画与特效应分组记录真实使用者，切换范围后释放无人使用的组，共用UI保留。当前有显式addRef及多个跨场景缓存，不能直接releaseAll。加载调度已按章节／本队限制，释放与资源分包尚未在本轮改动。

建议接续顺序：先做高占比图标的显示尺寸对照，再实现逐像素可还原的动画裁边，随后按背景和插画类别选择高品质编码；GPU格式与完整生命周期随后接入。以上未取得的收益不写成已压缩结果。
