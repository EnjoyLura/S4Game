# 密集弹幕性能优化 v79

用户要求先推送工程备份，再解决弓箭手连射、齐射较多时的卡顿，并检查其他性能开销。用户随后明确选择保留全部画面，先试玩本轮优化。

试玩地址：https://enjoylura.github.io/kingdom-watch-play/?v=performance-v79

## 本轮处理

| 开销 | 修改 | 保持的表现与规则 |
| --- | --- | --- |
| 箭矢、火球、冰锥、回旋弩矢每帧将上一帧节点全部停用，再逐个激活 | 保留已使用的渲染槽，仅在本帧数量减少时回收尾部槽 | 同样数量、同一池容量、同样素材与混合、同样场景顺序；数量归零时清理 |
| 倍速下同一显示帧可能模拟两次，每次都重建弹幕与粒子几何 | 继续逐步计算运动、碰撞、伤害、粒子寿命，只在最后一步绘制 | 每次命中音效、闪白、状态、穿透先后顺序保留；旧后备动画相位仍按模拟步递增 |
| 每支箭对全场怪物做精确扫掠 | 先检查保守包围框，排除绝不相交的目标 | 原线段/圆相交算法、同距顺序、lifeId 去重、穿透与折返结算代码保留；边界额外放宽 0.000001 |
| 箭光、风线、尾迹每层重复计算相同采样点、三角函数和幂函数 | 固定曲线只计算一次，动态中心线使用复用数组，多层绘制共享结果 | 保留所有采样点、光效层、颜色、宽度、透明度、绘制顺序，使用 JS 双精度数值 |
| 直线箭和子光效重复设置相同位置、朝向 | 仅在值改变时设置 | 原坐标、旋转、材质和动画保持 |
| 每次火焰绘制重新查找 UITransform | 创建时保留组件引用 | 包括灼烧同步在内只替换查找方式，完整 0.62 秒动画和每 0.5 秒扣血保持 |
| 拖尾移除旧点、连射查询、灼烧飘字限额和火焰预算反复创建临时数组 | 原位移动小型拖尾数组、循环求最短队列时间和计数 | 队列顺序、出箭时机、显示限额与所有预算不变 |
| 粒子每显示帧重新解析十六进制颜色 | 在粒子出生时解析，并复用池内颜色对象 | 原运动、形状、透明度和随机调用顺序保持 |
| 怪物覆盖层依次移动到最后，导致已经排好的两个节点反复换位 | 先确定冰脚层最上，再将死亡碎片固定在它下一层 | 最终遮挡顺序不变，地面阴影与角色仍逐步同步 |
| 防线中毒状态每步 filter 创建数组，包括空数组 | 原位稳定压缩 | 原伤害合并与扣血时间保持 |

没有减少箭数、连射排数、齐射列数、冰雨数量、特效层数、曲线段数、飘字限额或渲染分辨率；没有修改英雄/怪物数值、卡池、关卡密度、充能、两秒胜利收尾或存档。冰技能完整 v10 与 128 颗随机落冰保持。普通箭光晕/风线精简和分层合批等可能改变画面的方案本轮未采用。

## 用户手机试玩重点

1. 同样阵容、倍速与关卡下逐步叠加连射、齐射，观察密集出箭时的帧率和操作响应；对比时保持同样场景压力。
2. 箭矢密集时观察所有箭、绿色风线、金色拖尾，强化结束与清场后应正常收起，无上一帧箭影滞留。
3. 穿透、震退、分裂与回旋弩矢继续正常结算，检查受击声音和闪白；火球和冰锥视觉保持。
4. 灼烧扣血与完整火焰节奏、冰领域和冰雨、暂停/选卡/胜利两秒收尾保持正常。

若仍出现卡顿，优先记录手机型号、倍速、关卡与连射/齐射层数，再判断是否需要取舍普通箭叠加光效。当前用户选择先保留完整画面。
